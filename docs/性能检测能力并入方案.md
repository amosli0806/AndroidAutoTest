## 0. 结论先行

**这个 CLI 本质是一台"多进程 CPU / PSS 内存周期采样器"，外加 9 类可插拔的旁路采集器。**
真正值得抄的不是它的采样代码（我们的采样本项目已经有了，而且口径更干净），而是三样东西：

| 值得抄 | 为什么 |
|---|---|
| **采集器契约 + 统一收尾** | `PeriodicCollector` 把「怎么采」与「何时采、何时停」解耦，且在 `finally` 里统一 finalize —— 本项目现在是 hprof / 截图各挂一个 QTimer，缺统一的收尾 |
| **整机视角的 3 个采集器** | `top_sys`（整机进程/线程 CPU）、`meminfo_sys`（系统内存）、`smaps/dmabuf` —— 正好对应我们缺的「整机 CPU / 系统内存」 |
| **进程表配置驱动** | `process_list_dict`（85 个 `product.test_content` 组合）表达「一个产品由哪些进程组成」，可直接支撑「内存按全进程合并」 |

**不建议并入**：它的编排层（`general_package_monitor`，52 形参 / 1581 行）、HTML 报告（`PdhReport`，依赖 pandas+pyecharts 模板）、`cli_perf_test.py`（UI 自动化编排）、`-ex`（Monkey + 存活守护）—— 这四块与本项目已有能力重复且更弱。

**建议节奏**：P0 先并 `top_sys` + `meminfo_sys`（补齐扩展方向里明确点名的"整机 CPU / 系统内存"）→ P1 并 `smaps/dmabuf` + `iotop` + 录屏 + `netdev` → P2 再评估 `simpleperf` / `heap_profile`（都有 root 或 debuggable 前置条件）。

## 1. CLI 主入口的结构

| 项 | 事实 |
|---|---|
| 文件 | `mapauto_perf_test/cli_general-package-monitor.py`，378 行，**48 个命令行参数** |
| 形态 | `argparse` → 组装 `collectors=[...]` → 调一次 `general_package_monitor(...)` → 结束即退出 |
| 编排 | `my_perf_test/perf_data_monitor/perf_data_monitor.py`，1581 行；`general_package_monitor()` 在 1166~1551 行，**52 个形参** |
| 主采样 | **不可关闭**，`--test_content` 二选一：`top`（CPU）/ `meminfo`（PSS） |
| 采样节奏 | `--interval` 秒（默认 5）；`--duration` 分钟（默认 30，支持小数，0 = 按回车停） |

**三条路径都必须走到 `finally`**，否则汇总 CSV 与报告都不会生成。

## 2. 能力全清单

### 2.1 主采样（必开，二选一）

| `test_content` | 数据源 | 粒度 | 产物 |
|---|---|---|---|
| `top` | 解析 `adb shell top`（`-b`/`-H`） | 进程 CPU + 线程 CPU | `<product>_top.csv` / `_rslt.csv` |
| `meminfo` | 解析 `adb shell dumpsys meminfo` | PSS + 内存构成（java/native/code/stack/graphics/others/system） | `<product>_meminfo.csv` / `_rslt.csv` / `_completed.csv` |

**目标进程来自 `process_list_dict`**：85 个 `product.test_content` 组合，每项格式 `[进程名, 简化名, 采PSS, 采进程CPU, 采线程CPU]`，结果按多进程累加。产品名如 `autocar / naviauto / byd / audi / mona / mega / rox / zone / lingpao / huawei / mi`。

### 2.2 旁路能力（各自独立，互不依赖）

| 能力 | 开关 | 触发节奏 | 数据源 / 依赖 | 产物 |
|---|---|---|---|---|
| FPS | `--logcat_fps true` | 全程并行 | 解析 `logcat` 帧率 | 输出目录根 |
| 扩展内存 | `--ex_mem_interval >0` | 分钟级（仅采内存时生效） | 额外 PSS 采样 | 与主采样同文件 |
| 周期截屏 | `--screencap_interval >0` | 分钟级 | `screencap`（支持 `--display_id` 副屏） | `screencap/*.png` |
| 周期录屏 | `--screenrecord_interval` 且 `--screenrecord_time` 都 >0 | 分钟级 | `screenrecord` | `screencap/*.mp4` |
| Java 堆快照 | `--dump_heap_interval >0`（**默认 60，即默认开启**） | 分钟级 | `am dumpheap`（仅 debug 包） | `dumpheap/*.hprof` |
| smaps/dmabuf | `--smaps_interval >0` | 分钟级 | `/proc/<pid>/smaps`、`dmabuf_dump` | `smaps/*.txt`（只抓不分析） |
| 系统级 meminfo | `--meminfo_sys_interval >0` | 秒级，全程 | `dumpsys meminfo`（全局） | `meminfo_sys/` |
| 整机 top | `--top_sys_interval >0` | 秒级，全程 | `top`（整机进程/线程） | `top_sys/` |
| 网卡流量 | `--netdev true` | 后台线程，秒级 | `/proc/net/dev`，自动枚举全部网卡 | `netdev/netdev_<iface>.csv` + `_rslt.csv` |
| tcpdump | `--td_interval >0` | 整场只抓一次 | 设备侧 tcpdump；`--td_analyze` 自动调 pcap_report 解析 | `tcpdump/*.pcap` |
| heap profile | `--heap_profile true` + `--hp_path` | 整场只采一次 | heapprofd（内置 `third_party/perfetto/perfetto_heap_profile`） | `heap_profile/mem-out-<ts>/` |
| simpleperf | `--simpleperf true` | 整场只采一次 | 设备侧 `simpleperf record`（`shell` / `app` 两模式） | `simpleperf/perf-<ts>/perf.data` |
| iotop 磁盘 IO | `--iotop true` | 整场只采一次 | 设备侧 `iotop`（AOSP 版，线程粒度/系统全量） | `iotop/` 4 个文件 |

**开关的两种形态**（接入时容易做成两套逻辑）：布尔开关（FPS / netdev / heap_profile / simpleperf / iotop）与「数值 >0 才启用」（截屏 / 录屏 / 堆快照 / smaps / meminfo_sys / top_sys / tcpdump）。后者在参数层面 `0` 和 `5` 长得一样，UI 上必须显式标状态。

### 2.3 收尾产物

- `report.html`（`--report_type`，默认 `PdhReport`；置空则不生成）
- `device_info/report.html`：设备硬件/系统信息，**默认开启**，30 条 adb 命令串行约 10~15 秒
- `dumpsys_result/*.txt`：meminfo 原始输出按条件落盘
- `MPT_<时间戳>.log`：本次运行日志

### 2.4 明确不做

不做 UI 自动化、不做用例编排、不做评分、不做 Monkey/存活守护、不做符号化/火焰图渲染。
→ 与本项目重叠的部分（前两项）不并入。

## 4. 值得直接抄的四个机制

### 4.1 采集器契约（`collectors/base.py`）

```python
class PeriodicCollector:
    mode: str = 'once'      # 'once' | 'periodic'
    subdir: str = ''        # 产物落 {output_path}/{subdir}/
    interval: int = 0       # 触发周期（分钟）；0 会被过滤掉
    def bind_context(device_id, output_path, process_name=None)
    def bind_duration(total_seconds)     # "跟随整场"靠它（如 tcpdump）
    def start(self); def stop(self)
    def wait_for_completion(timeout=60)  # 等最后一次落盘
```

**两个配套函数解决了最难的两件事**（这是这套代码最值钱的部分）：

- `start_collector(collector, started_ids)`：once/periodic 统一调度 + **once 重入保护**。底层会话提前退出后不会被反复重开。
- `finalize_collectors(collectors)`：放在 `finally` 里，让「时长耗尽 / 回车停止 / Ctrl+C」三条路径都走 stop + wait，不会出现"只有原始 csv、缺汇总和报告"。

### 4.2 三类触发节奏要分清

| 节奏 | 例子 | 本项目对应做法 |
|---|---|---|
| 秒级采样（进曲线） | CPU / 内存 / FPS / 流量 | `PerfWorker.collect_sample()` |
| 分钟级旁路（不进曲线，落文件） | 截屏 / 录屏 / 堆转储 / smaps / top_sys / meminfo_sys | 现有 hprof / screenshot 的独立 QTimer 模式 |
| 整场一次性 | simpleperf / heap_profile / iotop / tcpdump | 开始监控时拉起、停止监控时收尾 |

**不要把所有能力都塞进 `collect_sample()`** —— 秒级循环里跑一次 10 秒的 `dumpsys meminfo` 会把采样节奏直接拖崩。

### 4.3 进程表配置驱动（`process_list_dict`）

把「一个产品由哪些进程组成」从代码里抽出来，格式 `[进程名, 简化名, 采PSS, 采进程CPU, 采线程CPU]`，按 `product.test_content` 索引。
本项目如果要做「内存按全进程合并」，这就是现成的表达范式 —— 但建议落到 `data/` 下的 JSON（对齐现有 `data/perf_baselines.json` 的风格），而不是写死在 py 里。

### 4.4 产物命名契约

`<进程名>_meminfo.csv`（原始）/ `_rslt.csv`（汇总，下游读这个）/ `_completed.csv`（按秒补全，画趋势用）。
若以后要和 mapauto 的历史数据对齐，字段名（`pss_avg/pss_max/pss_min/java_avg/...`）不能改。**本项目自用则无需迁就。**

## 5. 必须先解掉的六个冲突

| # | 冲突 | 具体位置 | 怎么解 |
|---|---|---|---|
| 1 | **设备通道不同** | mapauto 全用 `adb -s <id>` 子进程；本项目用 u2 `device.shell()`（`services/perf_compat.shell_text_checked` 提供 ok/text 契约） | 新采集器统一走 `device.shell()`，复用 `shell_text_checked` 的失败语义；只有**长跑设备进程**（simpleperf / iotop / tcpdump）才走 `subprocess + utils/adb_path.get_adb_path()`，并带 `-s device_service.serial` |
| 2 | **CPU 口径不同** | 本项目 = 多核累计（上限 = 核数×100，卡片写「多核累计」）；mapauto top = 单核归一（单核 100 上限） | 两套数值**绝不能进同一张卡/同一条曲线**。整机 CPU 若要画趋势，统一换算成「多核累计」口径，并在标题标注 |
| 3 | **内存口径不一致（已存在的坑）** | 本项目选主包时 CPU 覆盖 `包名:*` 子进程，内存却只算主进程（`dumpsys meminfo 包名` 只返回一个进程）—— 扩展方向第八章已列为待办 | **先修口径，再加新维度**。否则 `meminfo_sys` / `smaps` 一进来，"系统内存 vs 应用内存"对不上账。基线要加「口径」标记，避免旧基线被误判成内存上涨 |
| 4 | **采样节奏模型不同** | 本项目 `PerfWorker` 是单线程串行循环（`interval` 秒级、一条 `PerfSample`）；mapauto 是「1 秒 tick + 各 collector 按分钟到点触发」 | 保持本项目模型：秒级指标进 `PerfSample`，分钟级/一次性能力走独立定时器，产物落会话目录，不进曲线 |
| 5 | **隐性依赖 pymysql** | `perf_data_monitor.py` 顶层 `from collectors.logcat.logcat_fpsinfos import FpsDataMonitor`，而该模块顶层 `import pymysql` → **不用 FPS 也必须装** | 本项目已有 `numpy` / `Jinja2` / `pyecharts`，但**没有 pymysql**。所以只拷采集器、不拷编排层，天然绕过 |
| 6 | **静默失败的老毛病** | `interval=0` → `ZeroDivisionError`（`perf_data_monitor.py:1327` 等 5 处）；`product+test_content` 组合不存在 → **静默回落**到百度 naviauto 进程表；`--heap_profile` 但 `hp_path` 空 → 静默跳过 | 我们要的是「参数校验前置 + 组合不存在就报错」，别把这套静默行为带进来 |

另外两条只在用它自己的编排时才会遇到的坑：`meminfo_sys_interval` 与 `test_content='top_mem_all'` 写同一目录（勿同时用）；强杀进程（`taskkill /F`）会跳过 `finally`，只剩原始 csv。

## 6. 推荐接入方案

### 6.1 三条路，选 A'

| 路线 | 做法 | 评价 |
|---|---|---|
| A 逻辑移植 | 只把采集器的**解析逻辑与命令构造**搬过来，重写成项目内的 service | ✅ **推荐**。依赖干净、口径统一、UI 可控 |
| B 整体搬编排 | 把 `perf_data_monitor` + collectors 整目录拷进来 | ❌ 两套编排并存，会话模型打架，还带进 pymysql |
| C 子进程调 CLI | `subprocess` 调 `cli_general-package-monitor.py` | ⚠️ 仅适合"导出原始数据给外部"；不适合进本项目曲线/报告 |

### 6.2 A' 落点设计

新增一层 `services/perf_probes/`（与现有 `perf_service.py` 平级、互不耦合）：

```
services/
  perf_service.py            # 不动：秒级指标（CPU/内存/FPS/流量）
  perf_compat.py             # 不动：设备能力探测
  perf_probes/               # 新增：分钟级 / 整场一次性能力
    __init__.py
    base.py                  # 采集器契约（抄 4.1 的 bind_context/start/stop/wait_for_completion）
    top_sys.py               # 整机进程/线程 CPU      ← collectors/top/top_terminal_process.py
    meminfo_sys.py           # 系统级 dumpsys meminfo ← collectors/meminfo/dumpsys_meminfo_sys.py
    smaps.py                 # smaps + dmabuf         ← collectors/smaps.py
    iotop.py                 # 磁盘 IO（纯标准库）    ← collectors/iotop.py
    netdev.py                # 网卡流量              ← collectors/netdev.py
    screenrecord.py          # 周期录屏              ← collectors/screencap.py（录屏部分）
```

**四层改动清单**（每加一个能力，只动这四处）：

| 层 | 文件 | 改什么 |
|---|---|---|
| 采集 | `services/perf_probes/*.py` | 新探针；内部用 `device.shell()` + `shell_text_checked` |
| 调度 | `controllers/perf_controller.py` | 参照现有 `_start_hprof_loop` / `_start_screenshot_loop` 加起停；**停止必须走统一收尾**（现在是三处各自 stop，建议抽一个 `_finalize_probes()` 在 `_on_stop` 里统一调） |
| 模型 | `models/perf_model.py` | `PerfSession` 加 `probes: list[str]`（本次启用了哪些）与 `artifacts: dict`（产物路径），报告与「诊断产物」清单要用 |
| 视图 | `views/perf_view.py` | 指标组加复选框 + `_build_tool_cards()` 加卡片（现有卡片是"圆点 + 标题 + 控件一行"的 44 高模板，照抄即可） |

若某个能力要进曲线（如整机 CPU），才动 `PerfSample` + `_PERF_SAMPLE_FIELDS` + `get_stats()` + `compare_stats()` + 卡片 series。
**建议整机 CPU / 系统内存先只落文件 + 报告附图，不进秒级曲线**，避免改 5 个文件。

### 6.3 分期

| 期 | 内容 | 理由 |
|---|---|---|
| **P0** | `meminfo_sys` + `top_sys` | 扩展方向第八章点名的"系统内存 / 整机 CPU"；纯 adb 命令、无 root、无新依赖 |
| **P0.5** | 先修内存"全进程合并"口径 | 否则新维度一加，应用内存与系统内存对不上账 |
| **P1** | `smaps/dmabuf`、`iotop`、录屏、`netdev` | 都只依赖设备侧命令；`iotop` 纯标准库；`smaps` 是 native/dmabuf 细分的唯一来源 |
| **P2** | `simpleperf`、`heap_profile`、设备信息报告、tcpdump 自动 pcap 解析 | 各有前置条件（root / profileable / 二进制体积），收益偏诊断深挖 |

## 7. 验收口径

每个能力接入后按这套清单过一遍：

1. **开**：勾选 → 开始监控 → 产物出现在会话目录（`<输出目录>/perf/<会话>/...`，见扩展方向第四章的归档设计）
2. **停**：点停止 → 产物完整、汇总文件在、报告里有对应条目（不是只有原始文件）
3. **异常**：设备拔线 / 应用未运行 / 命令不存在 → 界面有明确提示，**不允许静默 0 或空文件**
4. **不干扰主线**：开启后秒级 CPU/内存采样间隔无明显漂移（`dumpsys` 类命令会抢 adb 通道，务必错开节奏）
5. **旧数据兼容**：旧 `perf_data.json` 能正常加载（新增字段全部有默认值）

冒烟命令（在 mapauto 侧对照，确认同名能力行为一致）：

## 8. 附：CLI 48 参数分组速查

| 组 | 参数 |
|---|---|
| 设备/项目 | `--device_id`（三态：空=省略`-s` / `auto`=自动选唯一设备 / 具体ID）、`--device_type`(pad/car/mi)、`--project_name`、`--case_name`、`--product_name` |
| 采样 | `--duration`(分钟，0=回车停)、`--interval`(秒)、`--test_content`(top/meminfo)、`--report_type`、`--output_path` |
| 旁路开关 | `--logcat_fps`、`--ex_mem_interval`、`--screencap_interval`、`--display_id`、`--screenrecord_interval`、`--screenrecord_time`、`--dump_heap_interval`、`--dump_heap_target_process`、`--smaps_interval`、`--smaps_target_process`、`--meminfo_sys_interval`、`--top_sys_interval`、`--top_sys_target_process` |
| 网卡 | `--netdev`、`--netdev_iface`（空=全部网卡）、`--netdev_interval` |
| heap profile | `--heap_profile`、`--hp_param_duration`、`--hp_param_interval`、`--hp_path`、`--hp_target_process` |
| simpleperf | `--simpleperf`、`--sp_duration`、`--sp_freq`、`--sp_mode`(shell/app)、`--sp_need_root`、`--sp_target_process` |
| iotop | `--iotop`、`--io_sample_interval`、`--io_sort`、`--io_need_root` |
| tcpdump | `--td_interval`、`--td_duration`、`--td_interface`、`--td_buffer_size`、`--td_need_root`、`--td_analyze`、`--td_device_ip` |

所有布尔参数接受 `1/true/yes/y/on`（大小写不敏感），其余为假。
