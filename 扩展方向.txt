===== 发版（2026-09-24 起用脚本，灵活可控）=====

脚本 release.py 支持多种模式（在项目目录 D:\AndroidAutoTest 打开命令行）：
    python release.py                     # 交互式菜单，逐步选要做什么（最直观）
    python release.py push                # 只上传代码到 GitHub main（不改版本号、不发版）
    python release.py 1.1.6               # 完整发版：改版本号→提交→推送→打 tag（触发 CI）
    python release.py 1.1.6 --no-release  # 改版本号 + 推送 main，但暂不打 tag 不发版
    python release.py 1.1.6 --dry-run     # 演练：只预览会改什么，不改文件、不提交
    python release.py --tag-only v1.1.6   # 版本号已改好时，只补打 tag 触发发版

日常节奏建议：
  - 平时改完代码 → 跑 `python release.py push` 同步到 GitHub（安全、不发版）。
  - 攒够一批改动想发版 → 跑 `python release.py 1.1.6`（自动改版本号+写 CHANGELOG 占位+提交+推送+打 tag）。
  - 发版前先 git pull 拉最新；脚本幂等，重复执行安全（同名 tag 会先删本地再重打）。
  - CHANGELOG 插入的是占位文字：发版前先手动改好 CHANGELOG.md 该版本段（脚本检测到已存在则不覆盖），或发完到网页编辑 Release 正文。注意别删掉 `## vX.Y.Z` 标题行。
  - 成功标准：push tag 后看到 "* [new tag] v1.1.6"；结果看 https://github.com/amosli0806/AndroidAutoTest/releases

手动兜底（脚本出问题时）：
  1. 改 utils/version.py 的 APP_VERSION
  2. 在 CHANGELOG.md 顶部加 "## vX.Y.Z" 段写说明
  3. git add -A && git commit -m "发布 vX.Y.Z" && git push origin main   ← 先传代码
  4. git tag vX.Y.Z && git push origin vX.Y.Z   ← 打 tag 触发 CI 发版

【语音播报】✅（回执验证为 v1.2.1 新增，v1.2.3 ~ v1.2.4 继续收口）
- 定位：声学耦合 —— 电脑扬声器放音，车机麦克风拾音后交给车机自己的语音助手，
  不与车机做任何协议对接；解决"声音从哪个扬声器出去"和"每句之间等多久"
- 三栏结构：语音管理（独立语音用例库：分组 → 用例 → 文案）/ 用例步骤（文案与检测步骤增删改 + 单条播报）/
  执行（勾选要播的用例、语速、循环、执行选中、停止）
- 语音用例管理：分组与用例的新建、复制（分组递归复制组内用例）、重命名、删除，
  右键菜单带图标并适配日夜模式；导入/导出 Excel 表格（一个分组一张工作表，三列 ——
  用例名称 / 操作步骤 / 预期结果，一个用例占一行；步骤与预期各自在单元格内换行 + 序号，
  预期序号即对应步骤号；导入按表名匹配分组、组内同名用例覆盖步骤）
- 步骤模型：播报步骤（文案 + 播后等待）与检测步骤（预期结果关键词，带绿色「预期」标记）混排；
  检测步骤永远作为"紧跟在它前面那句播报"的预期结果被执行；旧用例的全局成功关键词会自动迁移成检测步骤
- 回执验证：播报后抓车机 logcat 的反馈文案，按检测步骤的关键词判定这句有没有被正确识别；
  未命中不再中断执行（剩余步骤与用例照常跑完，最后统一提示「共 N 条未命中」），
  结果实时写入左下角「虫师日志」（日志只报结论，不贴车机原始日志）。
  · 日志标签支持一次填多个（空格 / 逗号分隔，如 TtsBusinessManager TestManager），留空则抓全量；
  · 验证只由检测步骤驱动 —— 没配检测步骤的播报一律不验证，设置页开关只作为总闸；
  · 播报页持有的配置与设置页写入的配置按字段合并，设置页改完不会被播报页的编辑改回
- 播后等待：按语速自动估算，「批量重算」一键**全量**重算所有用例的等待时间（不再只作用于当前用例）；每条步骤可一键复制
- 唤醒词：中栏「唤醒词」按钮一键把配置好的唤醒词追加成一条文案（未选用例时置灰），
  文案在「设置 → 语音设置」配置，留空回落到默认值，改完立即生效
- 执行：整行点击即可勾选；分组勾选级联；语速（SAPI -10~10）与循环次数；
  「停止」会立刻打断当前这句（后台线程持有 SAPI 对象，主线程调 stop() 打不断）
- 设置页拆成两页：
  · 「语音设置」：引擎 / 音色 / 输出设备 / 唤醒词，支持试听；在线音色库（含方言）；
    响度走系统音量，程序内不调音量
  · 「回执验证」：开关 / 日志标签 / 失败关键词（成功关键词按用例配在检测步骤里）
- 与「自动化编辑」里的语音播报步骤共用同一套音色、语速与输出设备配置；
  注意该步骤本身没有检测步骤的概念，因此不做回执验证

六、自动更新优化（增量更新）⚙️ 已落地（2026-09-29；收益从「支持增量的版本」的下一版开始）

已落地实现（本次）：
- 客户端 services/update_service.py：
  · 补丁发现：精确匹配资产名 patch-<起点版本>-to-<目标版本>.dpatch，且起点必须等于本机
    当前版本才可用（patch_available）；
  · 下载：抽出通用 _download_file，全量包与补丁共用一套（镜像 / 断点续传 / 重试 / sha256）；
  · 组装：apply_patch —— 按补丁 manifest 的完整文件清单，payload 里的用补丁内容，
    其余从本机旧安装复制，复制时顺带算 sha256 与清单比对；对不上就整体失败；
  · 调度：install_prepare 先走增量，**任何一步失败自动回退全量**（取消不算失败）。
- 生成端 make_update_patch.py：对比新旧两棵目录树，产出 manifest.json + payload/；
  payload 占比超过 --max-ratio（默认 60%）就判定"不值得发"直接跳过。
- CI .github/workflows/release.yml：checkout 加 fetch-depth 0；新增「生成增量补丁」步骤
  （gh release download 拿上一个 Release 的全量包 → 解压 → 调 make_update_patch.py），
  失败只跳过不阻塞发版；新增「校验全量包已产出」断言；Release 上传含补丁 glob。
- 自测 update_pipeline_selftest.py：覆盖「增量生成 → 组装与全量一致」「旧文件被篡改
  必须回退全量且仍成功」「没有补丁时不误判有增量」。

⚠️ 命名红线（必须遵守）：
- 补丁资产名**绝不能**带 .zip / -win64.zip / chongshi- 前缀。老版本客户端的 _pick_asset
  只挑 .zip、且优先认「chongshi- + -win64.zip」，一旦补丁长得像全量包，**旧客户端会把
  补丁当全量包下载**，解压后缺 虫师.exe/_internal，更新直接失败。现在这个名字对旧客户端
  完全不可见（其 .zip 过滤直接排除），零影响。
- **每次发版都必须照常产出全量 zip**，绝不做「只发补丁」的 Release（CI 已有断言兜底）。

顺带修掉的坑：download_asset 的下载重试分支里把 _DOWNLOAD_ATTEMPTS 写成了
DOWNLOAD_ATTEMPTS（少一个下划线），导致任何一次下载失败都会抛 NameError ——
断点续传/重试其实从未生效过。重构 _download_file 时一并修正。

背景（基于 dist 产物实测）：
- 现状每次更新都要重下整包（zip 约 290MB），因为 CI 每次重新打包整个 onedir 目录、
  压成一个 zip，update_service 只认这个全量包。
- 实测 dist/虫师 解压后约 609MB：PyQt6（Qt 动态库）约 489MB 占 80%，
  第三方库约 70MB、内置工具约 10MB，这些在版本之间基本不变；
  真正每次变化的只有业务代码（base_library.zip 约 1.3MB）。
- 结论：文件级增量更新能把下载量从 290MB 压到几 MB，收益巨大。

方案选型（按推荐度）：
1. 文件级 / 块级增量（首选）—— 新旧目录按文件分块、逐块算哈希，服务端只下发
   "变化的块 + 清单"，客户端在本地旧文件上重组出新文件。Qt 大库内容不变则一个块都不用下。
   参考：Electron Squirrel / Google Chrome / Steam / Windows Update。
   **本次采用「文件级」**（未做块级）：实测变化集只有 ~1.3MB，文件级已经拿到绝大部分收益，
   实现与校验都简单得多；将来若单个大文件频繁小改，再升级到块级。
2. 二进制差量（bsdiff / xdelta3 / zstd --patch-from）—— 对新旧包做 diff 生成 patch，
   实现最简单，但对已压缩的 zip 效果差（需对未压缩原始文件 diff，或用能感知压缩结构的工具）。
3. 架构分离（远期）—— 把运行时（Python + 第三方库 + Qt）与业务代码拆成两个包，
   更新只换业务包，收益天花板最高但改造最大。

GitHub Release 承载方式（已按此实现）：
- 一个 Release 挂多个资产：全量 zip + 增量补丁（相邻版本）。
- CI 构建时拉取上一个 Release 的包做 diff、生成补丁一起上传。
- 客户端 update_service 扩展：先找匹配当前版本的增量补丁，没有 / 失败则回退下全量。

需提前想清的坑（已处理 / 待观察）：
1. 版本矩阵：增量补丁只做相邻版本，跨多版本升级时回退下全量。✅ 已实现（精确名匹配）
2. PyInstaller 确定性：base_library.zip 里的 .pyc 可能带时间戳抖动，CI 已设
   SOURCE_DATE_EPOCH 固定；大块（Qt / 第三方库）稳定，不影响增量命中率。✅ 已加
3. 客户端打补丁加兜底：组装时逐文件 sha256 校验，失败自动回退全量。✅ 已实现
4. 补丁资产命名（新增，最要紧）：见上方「命名红线」。✅ 已用 .dpatch 后缀规避
5. 待观察：真实发版后看补丁体积与命中率，必要时调 --max-ratio 或引入块级增量。

优先级建议：作为独立迭代，先收尾 v1.2.x 车机实测再启动；主要工作量在 CI 端
（拉旧包、生成补丁）与客户端补丁逻辑，不碰现有稳定链路。

五、下一阶段开发规划（分阶段，按依赖与价值排序）
============================================================

规划原则：
- 优先「入口已在但内容是空的」模块（接口自动化）——补齐后功能全景才完整
- 优先「地基能力」（变量/参数化）——它是关键字驱动、数据驱动、CI/CD 的共同前提
- 每阶段可独立交付、独立验收，不做半成品

────────────────────────────
阶段一：接口自动化最小闭环 ✅ 已完成（2026-09-28）
────────────────────────────
交付内容（均已落地）：
1. 接口管理：接口列表（名称/方法 GET·POST·PUT·DELETE·PATCH·HEAD/URL/请求头/请求体/描述），
   增删改查 + 分组 + 复制 + 整份导入导出
2. 环境变量：多套环境切换，{{base_url}} 与自定义变量在 URL / 请求头 / 请求体 中替换
3. 断言引擎：状态码 + 响应取值（简易 JSON 路径）+ 包含文本 + 正则匹配 + 耗时上限，
   失败原因中文友好化
4. 执行与报告：单个发送 + 多选批量执行（可停止），HTML 报告落到「设置 → 输出目录」
5. 未做（转入接口模块二期）：与「自动化执行」用例互通 —— 它依赖阶段二的变量/参数化，
   见下方"接口模块二期"

────────────────────────────
阶段一·二期：接口模块二期（待排期）
────────────────────────────
1. 前后置脚本：Python 脚本钩子，处理签名、加解密、数据提取
2. 链路场景编排：接口串联，上一步响应作为下一步入参
3. 数据驱动：CSV / JSON / Excel 参数化，同一接口批量跑数据
4. 与「自动化执行」用例互通（需先有阶段二的变量/参数化能力打底）

────────────────────────────
阶段二：变量 / 参数化（目标 1~2 个版本周期）
────────────────────────────
现状：步骤 params 是纯字典，不支持 ${var} 占位；同一用例无法跑多组数据。

交付内容：
1. 全局变量表：定义设备序列号、测试账号、环境地址等，步骤参数中 ${var} 引用
2. 渲染层：DeviceService.perform 之前统一替换（元素库 + 步骤参数走同一层）
3. 变量作用域：全局 → 用例 → 步骤 三级，可覆盖
4. 数据驱动（依赖本阶段）：从 CSV/Excel 读取数据，同一用例循环多组数据

这是关键字驱动、数据驱动、接口与 UI 混合场景的共同地基，先做扎实。

────────────────────────────
阶段三：执行健壮性增强（目标 1 个版本周期）
────────────────────────────
直接关系用例稳定性与回归可信度，对「车机」这类慢响应场景价值突出。

交付内容：
