1. 测试套件增强 📋 方案已定 2026-11-23 · 待确认 4

现状：套件只是「一组用例 id」—— models/suite_model.py 的 TestSuite{name, case_ids}，没有 id（用名字当主键），存在 data/suites_data.json。执行页没有「执行套件」入口，是把套件用例勾进树里再点执行； CaseRunner.run() 其实已返回结构化的 RunResult（每条用例的 ok / duration_ms / steps / error），但 GUI 路径把它丢了，只靠解析日志统计通过/失败； 报告 utils/report_generator.py 只有一张整场成绩卡 + 日志流，没有套件名、没有逐用例明细。

要做两件事：① 套件级成绩单（含通过率与逐用例明细）；② 套件链式执行（A 跑完自动跑 B）。 两件共用同一套结构化结果，先把结果接住，再做展示。

① 套件成绩单：不重造统计，直接把 RunResult 落成报告。

  • 执行入口：执行页选中套件后，按钮从「执行选中」变为「执行套件」；控制器把 suite_name 一起传下去，结果写进 ExecutionModel.suite_result。 勾选集合与套件不一致时仍走原来的「执行选中」，避免误解。
  • 通过率口径：分母 = 实际执行单元（用例 × 数据行 × 轮次），跳过不计失败； 顶部同时给出「用例数 / 执行单元数 / 通过 / 失败 / 跳过 / 通过率」。
  • 报告结构：沿用现有 HTML 风格，新增 SuiteReport_<套件名>_<时间戳>.html， 排在现有 TestReport_ 旁边；逐用例一行（结果、耗时、失败步骤、错误摘要、截图链接）， 失败行可展开步骤明细。新前缀要同步进 report_list 的扫描白名单。
  • 不内嵌大图：只放截图相对链接（现有 TestReport 是 base64 内嵌，套件报告若照抄会把文件撑到几十 MB）。
Suites 执行结果（内存） { "suite": "全半屏操作", "started_at": "2026-11-23 15:02:31", "cases": [ {"name": "打开地图 - 全屏", "ok": true, "duration_ms": 4300, "steps": [{"index":1,"name":"点击全屏","ok":true}, ...]}, {"name": "打开地图 - 半屏", "ok": false, "duration_ms": 6100, "error": "未找到元素：iv_app_navi_mode", "screenshot": "shots/xxx.png"} ] }

② 链式执行：套件里加一个「执行完接着跑」的有序列表，语义是队列而不是嵌套。

  • 数据形态：{"name": "...", "case_ids": [...], "next": ["套件B", "套件C"]}； 老文件没有 next 字段，读出来就是空列表，不用迁移。
  • 执行语义：A 结束后按顺序跑 B、C；「失败即停」是全局开关，打开时任一环失败即终止整条链； 每环各自产一份套件报告，链结束再产一份汇总（各环通过率 + 总耗时）。
  • 防呆：保存时做环检测（A→B→A 直接拒绝）、套件不存在或已删除的引用置灰提示； 链最多 20 环，防手滑。
  • 改名风险：套件以名字为键，改名会断掉定时任务与链引用。v1 不改主键，只在改名时提示 「有 N 处引用」，并把引用自动跟着改（统一收口在 SuiteModel）。

兼容与影响面：suites_data.json 只增字段；CaseRunner 与 MCP run_suite 不动执行逻辑，只多返回 suite_name 与报告路径； 定时任务后续可直接复用 next（v1 不接，避免一次改两处调度）。

补充细节（容易漏的）

  • 报告元信息：套件名、设备序列号、虫师版本、开始/结束、轮次、是否失败即停、重试配置。 套件名可能含 / : * ? 等文件名非法字符，写文件前统一替换（套件名仍原样显示）。
  • 没跑到的用例要列出来：失败即停 / 手动停止后，剩余用例标「未执行」， 不计入通过率分母；数据驱动文件 0 行按「跳过」，不算失败。
  • 重试口径：重试成功只记最终「通过」，附「重试 N 次」；失败保留最后一次错误 + 每次重试摘要。重试不应产生多份套件报告。
  • 报告体积：成功步骤只留一行摘要，失败步骤才保存参数与错误全文； 否则一条长用例就能把 HTML 顶到几十 MB。
  • 报告位置与生命周期：与现有 TestReport_ 同目录 （输出目录/设备号/），不自动清理，保持一致。
  • 链式执行：每环独立 run_id 与套件报告；汇总报告只做聚合 （各环通过率 + 总耗时 + 断在哪一环），不复用单环 HTML。
  • MCP 边界：run_suite 返回值只增 suite_report 路径与 cases 明细；v1 不开放链式参数，由客户端逐个调用，避免一次改两个调度器。

3. 步骤级条件与循环 📋 规划中 · 方案已定 2026-11-21 · 待确认 3

现在步骤只能一条条顺序跑：弹窗在不在都得点，想重复一段只能复制粘贴。补两样 —— 条件步骤（满足才执行，否则跳过）与循环块（一段步骤重复 N 次）。

条件挂在步骤上，不做 if / else 块：车机用例九成是「有就处理、没有就跳过」， 真要 else 就写成两条条件相反的步骤，结果等价。判定复用断言那套 _get_ui_object(...).exists()，不另写一套逻辑。

循环用展开式：次数固定，执行前展开成 N 份（带轮次标记），执行器主循环不用动 —— 这是本方案最省事的地方。

case_steps: [ "step_1", {"kind":"loop", "count":3, "children":["step_2","step_3"]}, "step_4" ]
  • 老数据是纯 id 列表，原样能读；新增 get_structure() 给界面渲染块， get_steps_for_case() 仍返回扁平列表（内部展开）—— 执行器、控制器、MCP 共 7 处调用点一行不用改
  • 报告按轮次标注（2.3 = 第 2 步第 3 轮）；循环里失败仍走现有「失败即停」， 条件不满足记为「跳过」而不是失败
  • 交互：多选步骤右键「包成循环」；步骤卡片加条件按钮，拾取控件直接复用准星
  • 三个要防的坑：同一步骤 id 不能同时属于两个块（包成时校验）；步骤模板含块时要连结构一起存； 性能按用例归组时以整块为区间，报告序号要对得上轮次

补充细节（容易漏的）

  • 条件 v1 三类：元素存在 / 不存在、文本包含、文本等于（都复用断言的定位与超时； 文本类复用 ui_find 的 dump 缓存，不要每个条件各 dump 一次）。 变量比较不必单独做一种类型：条件参数里的 ${x} 由统一参数渲染替换 （2026-11-28 已落地，见第 5 章），写「文本等于 ${city}」即可。 数值大小与正则不做。
  • 条件超时默认 2 秒（可配 0~10）；超时按「不满足」处理并在日志标注， 避免每条条件都等满 5 秒把用例拖慢。
  • 循环约束：次数 1~999，空块不允许保存；循环体至少 1 步；展开后步骤数超过 5000 时拒绝执行并提示拆块，防止手滑写出无限长用例。
  • 模板兼容：TemplateModel 现在存的是步骤快照（templates[].steps）， 含循环块时必须同时存结构快照（新增 structure）；老模板没有该字段 = 纯扁平，照常能用。
  • 编辑操作：以块为单位复制 / 剪切 / 删除；把块内单步拖出前先解除块关系； 删除块要二次确认（块内步骤会一起删）。
  • 历史快照：结构变更仍走现有 5 秒防抖自动快照；前提是结构字段被 _signature 纳入变化检测，不能只看步骤正文。
  • 执行上下文：get_steps_for_case() 展开时给每步带 loop_index / loop_total / source_step_id；FailureContext 增加轮次字段，失败截图与 AI 分析能对上「第几轮」。数据驱动 × 循环的顺序是 「先数据行、再块内轮次」。
  • 与性能场景联动（第 5 项）：用例级时间区间不变，块只影响步骤序号与失败定位。

4. 接口模块二期 📋 规划中 · 方案已定 2026-11-21 · 待确认 4

已有的地基（不用重做）：{{变量}} 渲染（URL / 请求头 / 请求体三处）、 JSON 路径取值 json_get、状态码 / 耗时 / JSON 断言 —— 链路编排要做的只是把它们接起来。

① 链路编排（先做，约 3 天）：场景 = 有序步骤，每步引用一个已有接口（不复制定义）， 跑完按配置提取变量给下一步用。

场景「登录后下单」 1. POST /login 提取 token ← $.data.token 2. GET /cart 请求头 Authorization: {{token}} 3. POST /order 断言 状态码 = 200，失败即停
  • 变量优先级：上一步提取 > 前置脚本写入 > 环境变量。提取的是本次运行的真实值， 环境里的是默认值，只能兜底
  • 失败策略：默认「停」—— 链路有前后依赖，中间断了继续跑只会产生一堆假结果； 单步可改成「继续」，用于登出 / 清理这类收尾步骤
  • 改造量很小：run_case() 加一个 extra_vars 参数合并进变量表， ApiEnv 结构不动

② 前后置脚本（后做，约 2 天）：给一个 ctx，不给一堆 API。

def before(ctx): ctx.headers["X-Sign"] = sign(ctx.body, ctx.env["secret"]) def after(ctx): ctx.set("token", ctx.json["data"]["token"])
  • ctx 只有四类：请求（method / url / headers / body，可改）、 响应（status / headers / text / json / elapsed_ms）、变量（get / set）、日志（log）
  • 安全边界说实话：这是本机 Python，能读文件、能联网，做不了真沙箱。 做法是首次启用弹一次确认「脚本以虫师进程权限运行」；密钥不要写死，走环境变量
  • 脚本随导出走：否则换机器就丢了。导出 JSON 时提示「含可执行脚本」
  • 报错要带行号与源码片段，不能只丢一句「脚本错误」

补充细节（容易漏的）

  • 变量生命周期：提取值只存在本次运行上下文（内存），不写回 ApiEnv； 运行结束即清空。环境变量仍是默认值，避免「跑一次登录，之后所有场景都带着旧 token」。
  • 敏感信息：报告/日志里对 token / password / secret / authorization 一类键名做掩码；请求体与响应体默认各截断 4KB，避免报告过大与泄露。
  • 超时与重试：当前全局超时 15 秒、无重试；链路每步可单独配超时与重试（0~3 次）， 只对网络错误 / 5xx 重试，4xx 不重试。
  • 会话能力缺口：ApiService 每次请求独立，没有 Cookie / Session。 若链路依赖登录态，需要新增进程内 cookie jar（本次是否纳入见待确认）。
  • 请求体能力缺口：目前只有 JSON / 文本，没有 multipart 文件上传； 需要上传的场景只能先用脚本或外部工具。
  • 脚本执行边界：每次 before/after 限时 5 秒，超时按失败处理；异常必须带行号与 源码片段，不能只丢一句「脚本错误」。
  • 脚本随包走的安全：接口导出或数据包导入后，脚本第一次运行前再确认一次， 不能只信「本机首次启用」那一次确认。
  • 链路停止：复用现有 abort 机制，在步与步之间检查；正在进行的 HTTP 请求不强行中断， 等它返回或超时。
❓ 待确认（每条都附了推荐，不同意直接说编号即可）
  1. 链路是否需要 Cookie / 会话保持？
    建议：v1 纳入最小内存 cookie jar —— 「登录后下单」这类示例没有会话就跑不通；只保存在内存、不落盘、不做多账号。
  2. 是否需要 multipart 文件上传？
    建议：v1 不做 —— 车机接口以 JSON 为主，先看真实需求；需要时再补。

为什么先链路后脚本：变量提取用配置就能做；先上脚本的话，用户会拿脚本写「取 token 存起来」， 20 个场景就是 20 段重复代码。脚本只留给签名 / 加解密这类非敲代码不可的事。

💡 打个比方：前置脚本像「做饭前的备菜 + 上桌前的摆盘」——请求前先签名、加密， 响应后把数据提炼出来；链路编排像「接力赛」——上一个接口的返回，直接变成下一个接口的入参。

5. 性能检测补全 📋 规划中 · 细节补充 2026-11-23 · 待确认 4

已经有的：CPU / 内存 / 流量 / FPS / 线程都能采，堆转储、抓包、截图、录屏可随监控一起跑； 也能在监控期间顺带跑一组自动化或语音用例。失败现场截图、内存超阈值自动转储也都具备。 但产物与报告都是整场一份。

要做的「场景化联动」= 按用例归组，不是按用例重做采集：

  • 打点 + 采样归组（核心，零成本）：记下每条用例的起止时间戳，把这段时间的采样 算到它名下 —— 只是内存里按区间切，不额外碰设备，单条用例耗时几乎不变
  • 报告按用例分节：通过与否、耗时、各指标均值与峰值；失败或内存超基线的用例高亮， 能直接跳到它的截图
  • 截图 / 堆转储沿用现状：失败截图由执行层提供（已有），堆转储按整场间隔 + 超阈值自动触发 （已有），都不绑到用例边界
  • 抓包整场一份，事后离线切：执行结束后按用例起止时间戳切片，不占执行时间

GPU 指标暂不做：只有高通 Adreno 能取到，车机多为 Mali / PowerVR， SurfaceFlinger 只给帧统计；FPS 已经覆盖「卡不卡」的主要判断。

刻意不做的：每条用例都转储、每条用例重启抓包。堆转储走 am dumpheap，会触发强制 GC 让被测应用短暂冻结 —— 不只拖慢，还可能让 「3 秒内出现」这类基于时间的断言超时，变成假失败；抓包每条重启则会丢包。 这两样都放在执行路径之外，是这条路「不增加用例耗时」的关键。

产物长什么样（目录骨架沿用现有 {输出目录}/{设备号}/perf/{会话名}/）：

├─ cpu/ mem/ netdev/ fps/ 整场采样（不按用例切） ├─ hprof/ 整场按间隔 + 超阈值触发 ├─ screenshots/ 失败截图（已有） ├─ packet/ │ └─ capture.pcap 整场一份，边跑边抓 ├─ cases/ 新增：每条用例的元信息与指标汇总 │ ├─ 01_打开地图.json │ └─ 02_搜索.json └─ perf_report_2026-11-21_1502.html

cases/01_打开地图.json 存这条用例的起止时间与该区间的汇总值： started_at、duration_ms、ok、 cpu_avg / cpu_peak、mem_peak_mb、 fps_avg、traffic_kb，以及 screenshot / pcap 的指向。 报告与后续对比都读这份，不用再解析整场采样。

报告新增一节「🕒 场景化 · 按用例」，排在「测试详情」之后，一行一条：

pcap 切包先别做：editcap（Wireshark CLI）能按时间切，但要随包带几 MB； scapy / dpkt 是新增依赖。零依赖的做法是不切文件 —— 报告里给出每条用例的时间范围（如 15:02:31.4–15:02:37.9），需要时在 Wireshark 里按时间过滤。 等真嫌麻烦再把 editcap 打包进去。

补充细节（容易漏的）

  • 事实基础：自动化场景在 services/perf_runner.py 里已经拿到了 CaseResult（用例名 / ok / 耗时 / 错误），缺的是起止时间戳；语音场景走 VoicePlaybackRunner，目前没有用例级回调，要另加打点。
  • 时间基准：用例边界与采样点都用主机单调时钟；设备时间只用于日志展示， 避免车机与 PC 时差导致区间错位。
  • 采样不足：用例时长小于采样间隔时，取区间内最近一个采样点并标注 samples=1；完全没有采样则字段为 null，报告显示「—」而不是 0 （0 会被误读成「没消耗」）。

  • 流量口径：netstats 是累计值，按区间首尾差值算；短用例可能为 0，报告标注 「采样不足」。跨 UID 的后台流量不算进被测应用。
  • 失败截图归属：用 FailureContext.timestamp 落到对应区间； 同一用例多张截图都保留，报告只展示最后一张 + 「更多」。
  • 桥接方式：CaseRunner 增加可选 on_case_start / on_case_end 回调（不依赖 Qt），GUI、性能、MCP 共用；不改现有进度回调语义，避免连锁修改。
  • 报告性能：曲线按需加载（点开某行再读对应 json），首页只渲染汇总表， 几十条用例的会话也不至于打开就卡。
  • 基线对比的缺口：现有基线是整场会话级；要按用例对比，基线必须带 case_key（用例名 + 步骤数），否则同名用例跨版本对不上。v1 先只做 「本场 vs 上一场同套件」。

6. 关键字驱动 📋 规划中 · 方案补充 2026-11-23 · 待确认 4

把常用动作组合封装成「关键字」（如「登录」「搜索商品」），支持传参，用例里点一下就复用。

它和「步骤模板」不是一回事（这两个最容易混，先分清）：

对比项步骤模板（已有）关键字驱动（本项）
插入后变成 5 个普通步骤，能逐条改只留一步「调用 登录」
改定义已插入的不会跟着变所有调用方一起变
参数不支持，值原样复制支持传参（账号 / 密码）

一句话：模板是「复制一份」，关键字是「引用一份」。 前者解决「懒得重复拖步骤」，后者解决「改一处、全都变，而且每条用例参数不同」。

方案细节（v1 形态）

  • 定义存哪：新增 data/keywords_data.json（第 12 个用户资产）， 必须同步进 HistoryModel.TRACKED_FILES 与数据包备份的清单 —— 这是最容易漏的一处。
  • 定义结构：{id, name, params:[{name, default, required}], steps:[...]}； 步骤仍是普通 Step 快照（与 TemplateModel 同构），不引用原用例步骤 id。
  • 调用方式：新增步骤类型 keyword， params={keyword_id, args:{账号: ..., 密码: ...}}； 执行时展开而不是保存时展开 —— 改定义立即对所有调用方生效。
  • 参数取值：v1 支持字面量与 ${变量}，不做类型系统；参数替换发生在 展开后的内部步骤参数上，复用现有 resolve_params。
  • 嵌套与环：允许关键字内部再调用关键字，深度上限 5；保存时做环检测（A→B→A 拒绝）， 运行时再做一次兜底，防止手改 json 造成死循环。
  • 失败与报告：内部步骤按 2.3.4 编号（外层步骤.内层步骤）； 失败上下文带「关键字名 + 实参」，截图照常；AI 分析能看到真正失败的内层步骤。
  • 删除与修改保护：被引用的关键字不允许直接删除，先列出调用方； 改定义时提示「影响 N 条用例」，保存后立即生效（不做版本化）。
  • 导出：用例导出必须附带被引用关键字定义，否则对方打开是断链； 数据包自然包含；单条用例的 JSON 导出需要新增 keywords 段。
  • 元素引用：内部步骤引用元素库 id，删元素时与普通步骤一样走「引用健康检查」， 失效时能逐条重拾取。
  • UI 入口：不新建左侧页面；在「用例编辑 → 步骤模板」入口旁加「关键字库…」对话框 （列表 + 编辑 + 试运行单个关键字）。

    建议：v1 不做，全部按文本替换；坐标/数字的合法性由具体步骤执行时校验。

目标：把虫师跑在 Mac 上，连车机做同样的测试。下面按「不改就跑不起来 / 能跑但行为不对 / 已经写好不用动」三类梳理，每条都标了确切文件；第五、六节分别为 2026-10-14 与 2026-11-19 的复核补充。

一、不改就跑不起来

  • 依赖装不上：requirements.txt 里的 pywin32 / pywin32-ctypes 是 Windows 专有，macOS 上 pip install -r 会直接失败。要按平台拆（requirements-win.txt / requirements-mac.txt），或加环境标记 pywin32; sys_platform == "win32"。
  • 离线语音是 Windows 专有：services/voice_service.py 的 WindowsSapiEngine 走 win32com + SAPI。macOS 要么接系统 say / NSSpeechSynthesizer，要么只用跨平台的 Edge 在线语音（EdgeTtsEngine 已实现）。main.spec 里登记的 win32com.client / pythoncom 也要按平台去掉。
  • 数据会写进 .app 里：utils/app_paths.py::get_app_dir() 返回「exe 同级目录」。macOS 打包后 sys.executable 在 虫师.app/Contents/MacOS/ 内，往那儿写 data/ 会破坏 bundle（/Applications 下还可能只读，代码签名校验也会判为被篡改）。应改为 ~/Library/Application Support/虫师/。
  • 日志同样会写进 .app 里：utils/logger.py 的 LOG_DIR = "logs" 是相对路径（相对当前工作目录），main.py:55 的 app_debug.log 也是裸文件名 —— 打包后随启动方式不同会散落在 bundle 内或任意 cwd。要一并归到 ~/Library/Logs/虫师/（或与 data 同级的 ~/Library/Application Support/虫师/logs/）。
  • 打包脚本是 Windows 形态：main.spec 用的是 EXE(manifest=…)（Windows DPI 清单）、icon=.ico、COLLECT onedir。macOS 要改成 BUNDLE(...) + .icns，产物是 .app 目录。两个 spec（main / updater）各自都要处理。好消息：resources/icons/app_icon.icns 已经在了，图标素材不用另做；main.spec 里那段 _MANIFEST（DPI 清单）只在 Windows 有意义，macOS 分支要整个去掉，否则 PyInstaller 会报错。

三、配置方式与优先级

命令行参数写在客户端的 mcpServers 里，改一次要重开客户端，很别扭。 所以主入口放在虫师自己的配置文件里，命令行只做临时覆盖。

// <安装目录>\data\mcp_config.json（可选；不写 = full）
// 发布版为 D:\虫师\data\mcp_config.json；开发目录为 D:\AndroidAutoTest\data\mcp_config.json
{
  "tools": {
    "profile": "core",          // core | standard | full
    "add": ["gen", "ops"],      // 在 profile 基础上追加的组
    "remove": ["monkey_start"]  // 从结果里摘掉的单工具（组名也可）
  }
}

优先级：命令行 --tools= > 配置文件 > 默认 full。 这样三种人都照顾到了：

  • 不配的人：什么都不用管，就是 full（73 个，与升级前一致）
  • 阶段性调整的人：在 data/mcp_config.json 里改一行，下次连接生效，不碰客户端配置
  • 临时覆盖的人：命令行 --tools=core,gen,-save_case

命令行语法（与配置文件等价）： --tools=core,gen,ops（组叠加）、--tools=-monkey_start（从 full 排除单工具）、 --tools=full（全开）。启动日志会打印实际暴露数量，例如 MCP 工具：命令行 --tools=core，暴露 16/73 个。

预设定义：core = core；standard = core + content； full = 全部（默认）。standard 是给「既要执行、也要维护用例」的场景用的。

配置文件是可选的：不存在时按默认 full；不会在启动时自动生成， 需要收窄时手工创建 data/mcp_config.json 即可。

四、可发现性：主动收窄后，怎么让人找得到

先讲清机制：MCP 客户端在连接时向 server 要一次工具清单，把清单连同参数说明注入模型上下文。 模型能用的只有清单上的东西；不在清单上的，它不但调不了，而且根本不知道存在 —— 这不是「没权限」（会说需要授权），而是「不知道」（会让用户手动操作）。

B 方案下默认是 full，gen 一直在清单里，不存在「找不到」的问题； 只有用户主动切到 core 且没有 add: ["gen"] 时才会遇到。 对这类用户，当前补偿方式是文档 + 启动日志：

  • README / 帮助中心写明四个组分别包含什么，以及「需要现场生成用例时加 gen」；
  • 启动日志打印 MCP 工具：配置 profile=core，暴露 16/73 个， 用户能立刻看出自己收窄了哪些能力。

没有往 list_cases / run_case 的 description 里加提示： 那会改变已实测的 schema 预算，而且默认 full 时并不需要。如果以后把 core 改成默认， 再把「缺少用例时提示开启 gen」补进 description。

💡 打个比方：工具清单就是工作台面上摆出来的工具。默认全摆在台面上； 用户自己把三件收进抽屉时，我们至少在抽屉上贴张字条（文档 + 启动日志）。

五、设计决策记录（为什么这样，为什么不那样）

① 为什么 B 保留 full 默认：不在清单里的工具对模型是静默消失 （既不能调，也不知道存在），而 1.6.0 本身已经有 MCP 接入、weditor 下线、依赖大改等变更； 默认切 core 会把「省 token」与「工具突然不见了」混在一起，很难归因。 先用 opt-in 收集真实使用数据，再决定是否改默认。 至于 core 本身为什么不含 gen：用例总量有上限、集中在项目初期， 中后期以回归和零星补充为主；1173 字符（全量 11%）换一个阶段性能力不划算 —— 这是 「切 core 时」的取舍，不是当前默认。

② 为什么不按工具名前缀自动分组：现有命名是动词开头 （list_cases / save_case / run_case / explore_and_draft / press_key / launch_app）， 按 _ 前缀分会碎成 26 个组、其中 13 个各只有 1 个工具。 所以必须显式标注组（当前维护一张 mcp_server/tool_groups.py 映射表）。 兜底防烂：未标注的工具自动进 core，不会变成「找不到」； 当前 73 个工具均已标注，启动日志会打印实际暴露数量。

③ 为什么不做运行时动态增删（notifications/tools/list_changed）： 协议支持，但客户端实现参差，常见「列表刷新了、模型还在用旧的」；收益远小于麻烦， 改配置后重连一次反而确定。

④ 为什么不做懒加载（先给 8 个，模型需要时调 request_tools 加载更多）： 多一轮往返，且多数模型不会主动去加载，「不知道自己不知道」的问题反而更严重。

六、由此发现的一个新能力：跑完回存

讨论「横展」时发现一个比 explore_and_draft 更贴合真实动作的工具：

save_run_as_case —— 把一次 run_case 实际执行过的步骤（含每次点击命中的 控件与定位值）存成新用例。

⚠ 前置改造（当前不具备）：run_case 的 StepResult 只有 index / name / type / ok / message / screenshot，没有 params； CaseRunner 只在失败上下文里记录 step_params， 成功执行时并没有留存命中的控件与定位值。要实现「含定位值」，需先让 CaseRunner / DeviceService 在成功执行时也记录步骤参数与命中元素， 约 100~150 行；工具本身约 50 行，不能按「只加一个工具」估算。
💡 为什么它比「边探索边记」更实用：横展到新车型时的真实动作是 「先在这个界面上手点一遍看能不能跑通」，跑通了才想「这套步骤存下来」。 explore_and_draft 适合全新流程，而这个适合验证成功后回存。 横展到别的项目时，这套已存的用例还能用 case_copy（content 组）直接复制。

归属：gen 组；触发提示挂在 run_case 的返回里 （「本次执行 8 步，如需存为新用例，开启 gen 组后用 save_run_as_case」）。

横展的两种情况要分开：
① 同构横展（新车型界面一致）→ 复制已有用例改定位，case_copy + element_upsert 就够， 不需要 gen；
② 异构横展（界面不同、旧用例全废）→ 才需要重新探索/回存，走 gen。

三、其他未修问题

实现位置

三个容易踩的点

  • 语音页没有数据驱动：中文表头的 CSV（${账号}）在自动化里能跑通， 留在语音页会念出字面量并告警 —— 因为没有「当前这一行数据」这个概念
  • 元素库也能写变量：定位值写成 ${包名}/id/btn 一样生效， 因为替换发生在元素解析之后。换 App 只改一个变量
  • 唤醒词不渲染：它来自设置，属于环境配置；万一里面恰好有 $， 渲染会把字面量吃掉，所以刻意跳过
💡 一句话记住：语法是同一套，差别只在「变量从哪来」—— 自动化能拿到 CSV 当前行的值，语音页只能拿到全局表和内置变量。
