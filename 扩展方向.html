1待办与扩展方向（按改动量排序）

从「改动小、见效快」到「改动大、影响面广」依次排列 —— 越靠前越建议先动。档位只反映改动量与风险，不代表价值：D 档（如关键字驱动）一旦做出来收益最大，只是要先有变量地基。

1. 测试套件增强 📋 规划中

  • 套件级执行报告与通过率　套件链式执行（A→B）
💡 打个比方：像「歌单」——用例按「冒烟测试」「回归测试」分组，跑完自动出这份歌单的「成绩单」（通过率），A 歌单放完自动放 B。（还差「成绩单」和「连着放」。）

2. 步骤模板 📋 规划中

保存常用步骤组合为模板（如「启动应用 → 等待 → 点击首页」），任意用例里插入复用。

💡 打个比方：像 Word / PPT 模板——「启动 → 等待 → 点首页」这套成熟流程存成模板，新用例直接套用，不用每次从零搭。

3. 知识库增强（检索与关联）📋 规划中

现状：views/knowledge_view.py（1329 行）+ models/knowledge_model.py（747 行） 已具备「项目 → 分类 → 笔记」树、富文本编辑器（落库转 Markdown）、标签、全文搜索、图片资源、Markdown 导出。 基础功能够用，但提效交互仍然偏少。

💡 打个比方：现在的知识库像一本装订整齐的笔记本 —— 纸和目录都不缺， 缺的是书签、索引卡和「上次看到哪儿」。

三个短板：① 无大纲，长笔记只能靠滚动；搜索也得切到搜索页； ② 只有行内代码（toggle_code），没有代码块，而内容里全是 adb 命令； ③ 笔记之间完全孤立，没有关联与反向链接，「踩坑」和「环境信息」互相指不到。

六个改造点（按投入产出排序）：

  • 代码块 + 高亮 + 复制 + 一键发到 ADB 工具箱执行（约 0.5 天）：贴合度最高 —— 复制完直接跑， 省掉切页面粘贴
  • 速查字段卡（约 0.5 天）：把包名 / 启动 Activity / 账号做成键值行 + 一键复制， 把「翻笔记复制」变成「点一下」
  • 命令面板 Ctrl+P（约 1 天）：跨项目搜标题 / 正文 / 标签，还能直接执行 「新建笔记」「切换项目」。注意 Ctrl+K 已被「插入链接」占用，别撞键
  • 右侧「大纲 + 被引用」面板（约 1 天）：长笔记的结构感
  • 双链 [[笔记名]] + 反向链接（约 1.5 天）：在「踩坑」里写 [[环境信息]]， 右侧自动列出反向引用
  • 标签聚合视图（约 0.5 天）：模型里 all_tags() 已有，只差 UI，用来跨项目看「同一类坑」

差异化：一键记坑（别的工具没有）—— 在「自动化执行」的失败结果或「性能检测」的劣化告警上右键 「记为踩坑」，自动建笔记并填入设备型号、包名、失败步骤、日志尾部 50 行、当前截图， 自动挂到对应项目的「踩过的坑」下。测试真正浪费时间的是「事后回忆现场」，这条直接把现场钉住， 且完全复用已有的截图 / 日志 / 报告能力。

不改数据结构：以上全部落在视图层 + KbNote 现有字段上，Markdown 落库流程、 既有导入导出都不动。

开源参考（抄交互，不嵌代码）：VNote（Qt/C++，三栏 + 大纲 + 标签 + 多标签页， 技术栈同源，交互可直接平移）、QOwnNotes（Qt/C++，极简笔记列表的手感）、 思源笔记 SiYuan（块级引用 / 双链 / 反链面板，双链交互最好的范本）、 Trilium（层级 + 属性视图）、Logseq（命令面板与大纲的联动）。

🚫 不建议整包集成：AppFlowy / AFFiNE / Joplin / Outline 都要 Electron 或服务器， 与「绿色免安装桌面工具」的定位冲突，且安装包已经较大（1.5.24 约 440MB，移除 QtWebEngine 后会下降）。
✅ 可嵌的组件：markdown-it-py + QTextBrowser（Qt 原生，不再依赖 QtWebEngine）、 highlight.js / mermaid / KaTeX（离线打包即可）、 SQLite FTS5（Python 标准库自带，笔记量大时再上）。

建议起步：代码块 + 一键发 ADB（0.5 天）→ 速查字段卡（0.5 天）→ Ctrl+P 命令面板（1 天）。 三个做完「好用感」有明显质变，且都不动数据模型。

2macOS 移植注意事项 📐 2026-10-10 初评 · 2026-10-17 复核 · 未开始

目标：把虫师跑在 Mac 上，连车机做同样的测试。下面按「不改就跑不起来 / 能跑但行为不对 / 已经写好不用动」三类梳理，每条都标了确切文件；第五节为 2026-10-14 二次核查的新增发现。

一、不改就跑不起来

  • 依赖装不上：requirements.txt 里的 pywin32 / pywin32-ctypes 是 Windows 专有，macOS 上 pip install -r 会直接失败。要按平台拆（requirements-win.txt / requirements-mac.txt），或加环境标记 pywin32; sys_platform == "win32"。
  • 离线语音是 Windows 专有：services/voice_service.py 的 WindowsSapiEngine 走 win32com + SAPI。macOS 要么接系统 say / NSSpeechSynthesizer，要么只用跨平台的 Edge 在线语音（EdgeTtsEngine 已实现）。main.spec 里登记的 win32com.client / pythoncom 也要按平台去掉。
  • 数据会写进 .app 里：utils/app_paths.py::get_app_dir() 返回「exe 同级目录」。macOS 打包后 sys.executable 在 虫师.app/Contents/MacOS/ 内，往那儿写 data/ 会破坏 bundle（/Applications 下还可能只读，代码签名校验也会判为被篡改）。应改为 ~/Library/Application Support/虫师/。
  • 日志同样会写进 .app 里：utils/logger.py 的 LOG_DIR = "logs" 是相对路径（相对当前工作目录），main.py:55 的 app_debug.log 也是裸文件名 —— 打包后随启动方式不同会散落在 bundle 内或任意 cwd。要一并归到 ~/Library/Logs/虫师/（或与 data 同级的 ~/Library/Application Support/虫师/logs/）。
  • 打包脚本是 Windows 形态：main.spec 用的是 EXE(manifest=…)（Windows DPI 清单）、icon=.ico、COLLECT onedir。macOS 要改成 BUNDLE(...) + .icns，产物是 .app 目录。两个 spec（main / updater）各自都要处理。好消息：resources/icons/app_icon.icns 已经在了，图标素材不用另做；main.spec 里那段 _MANIFEST（DPI 清单）只在 Windows 有意义，macOS 分支要整个去掉，否则 PyInstaller 会报错。

二、能跑，但行为不对

  • 自动更新整体不可移植：updater.py 靠「等主程序退出 → 改名替换 exe 与 _internal」做热更新，全程 Windows API（kernel32 等进程、EnumProcesses 找占用者）。macOS 的 .app 是目录，且有 Gatekeeper / 公证与签名校验，替换内部文件会让应用起不来。macOS 上应改用 Sparkle 之类，或「下载 dmg → 引导用户替换」。
    补充：updater.py 顶层只 import ctypes（安全），ctypes.windll 都在函数内 —— 所以它不会 import 期崩，但一跑到 wait_for_exit() / 找占用进程就必然 AttributeError；且文件里没有任何非 win32 早退。macOS 上要么整条链路按平台禁用（主程序侧不提示「下载并更新」），要么重写。
  • 菜单栏托盘的平台差异不止提示语：macOS 托盘在菜单栏，setToolTip 无效、activated 的 Context 语义与 Windows 不同（左键单击即弹菜单是常态）、没有「双击」；自绘快捷面板（views/tray_controller.py）需按平台调整，或干脆改用原生 QMenu。注意：托盘面板里的「打开输出目录」还踩了上面那条 os.startfile 的坑。
  • 系统级通知：controllers/notification_controller.py 走 QSystemTrayIcon.showMessage（跨平台可用），但 macOS 的横幅通知需要用户授权、且「关闭最小化到托盘」的交互习惯不同（Mac 习惯关窗不退、由 Dock 收回），文案与默认行为都要重新考虑。
  • 单实例保护：现在用 Windows 命名互斥体（main.py::_acquire_single_instance，非 win32 已直接放行）。macOS 上要换成 QLocalServer 或文件锁。
  • 子进程「父死子亡」（ADB 命令池）：这条目前靠 Windows Job Object 兜底 —— 实现已抽到公共模块 utils/win_job.py::bind_kill_on_close()，由 services/adb_command_pool.py（ADB 指令）使用（v1.4.8 修「残留一堆 adb 孤儿进程」时并入）。它在非 win32 直接返回 True（等于不绑），所以 macOS 上这层保护是空的：正常退出还能靠主动清理（_kill_process_tree / stop_all / atexit）收掉，但被强杀或崩溃时收不住（Windows 恰恰靠 Job Object 兜这两条路径）。macOS 没有等价的内核机制，只能把「进程组 + 退出时 kill」这条正常路径做扎实，或另找 launchd 之类的方案。
  • 字体：utils/theme.py 写的是 'Segoe UI', 'Microsoft YaHei'，日志区与报告的等宽字体是 Consolas —— 这些在 macOS 上都不存在。中文会由系统挑 CJK 回退、不至于乱码，但等宽字体要补 Menlo / SF Mono。views/splash_window.py 的 QFont('Microsoft YaHei')、utils/perf_report.py 与 views/help_view.py 的 HTML 字体同理（utils/api_report.py 已经带了 PingFang SC，可照抄）。
  • 内置工具是 Windows 二进制：tools/ 下的 scrcpy.exe 与一堆 dll（SDL2.dll／avcodec-61.dll／libusb-1.0.dll 等）只能在 Windows 用，macOS 要换 mac 版 scrcpy（建议改走 brew install scrcpy，同时把 tools/ 的 Windows 文件从 mac 包里排除）。（tools/take_help_screenshots.py、import_*.py 是开发脚本，不随包发布，可不管。）utils/adb_path.py 已按平台返回 adb / adb.exe，但 macOS 上得让用户 brew install android-platform-tools，帮助中心的安装指引（views/help_view.py「环境准备 → 安装 adb」）整段是 Windows 截图 + D:\platform-tools + 环境变量操作，需要一套 mac 版文案与截图。
  • 「打开所在文件夹」有四处是坏的：controllers/notification_controller.py、controllers/execution_controller.py、controllers/api_controller.py 用的是 os.name == 'nt' → os.startfile，否则 xdg-open，而 macOS 上没有 xdg-open，点了会静默失败；views/tray_controller.py::_open_output_dir（托盘面板「打开输出目录」）更彻底 —— 直接 os.startfile(p)，连平台判断都没有，macOS 上会抛 AttributeError。四处都应统一成 win32 / darwin / else 三分支 —— controllers/perf_controller.py 里已经是正确写法（os.startfile / open / xdg-open），照抄即可。
  • 字体还有漏网的（不止 theme.py）：除 utils/theme.py 的 'Segoe UI','Microsoft YaHei' 与 Consolas 外，还有 utils/dialogs.py:512 的 QFont("Segoe UI")、main.py:750 与 views/logs_view.py:165 的 QFont("Consolas", 10)、views/adb_dialogs/search_results_dialog.py 的 f.setFamily("Consolas")，以及一批 QSS 里的 font-family: Consolas, monospace（main_window / notification_center_view / perf_dialogs 等）。统一补 mac 回退：正文 PingFang SC、等宽 Menlo／SF Mono。
  • web 报告字体也不只是 perf_report：utils/report_generator.py:42（测试报告）用 'Segoe UI', Tahoma…、utils/perf_report.py:427 用 'Segoe UI','Microsoft YaHei'、views/help_view.py:918 同理 —— 都要照 utils/api_report.py 的做法带上 PingFang SC。

三、已经写好，不用动

  • subprocess.CREATE_NO_WINDOW：全项目都写成 if sys.platform == 'win32' else 0，非 Windows 传 0。
  • utils/adb_path.py：adb / adb.exe、scrcpy / scrcpy.exe 已按平台取名。
  • utils/wireless_manager.py：ping 次数参数 -n（Windows）/ -c（其他）。
  • services/adb_command_pool.py 的 _kill_process_tree()：Windows 走 taskkill /PID /T /F；POSIX 走 os.killpg(os.getpgid(pid), SIGTERM→SIGKILL)（配 preexec_fn=os.setsid 让子进程自成一个进程组），两处都套了 try/except —— macOS 可用。

💡 打个比方：智能体是刚空降的工程师，虫师是干了三年的老师傅。 工程师说「我要点播放」——老师傅知道那个按钮在哪一屏、要不要先滑一下、等它加载多久、 点不中换哪个定位值。工程师负责决定，老师傅负责真的点到。

所以角色定位是：虫师不是「AI 帮你写用例的测试工具」，而是 智能体的执行层——它决定去哪，虫师负责稳稳地到。

⚠ 接入前必须确认的两件事
① 对方是否支持本地 stdio——部分平台只开放远程 streamable-http，不接受本地进程启动。 虫师连的是 USB 设备，只能在本机跑；遇到只认 HTTP 的平台，就得自己加一层 「stdio ↔ 本地 HTTP」桥接，多一层就多一个故障点，能不做就不做。
② 锁死 SDK 版本——MCP 协议本身还在快速演进（2026-06 企业级授权扩展稳定、 2026-07 从有状态连接改为无状态连接）。requirements.txt 里写 mcp==x.y.z 而不是 mcp>=，否则客户端一升级，server 可能直接起不来。
场景约定
只开 MCP，GUI 没开正常，独占设备；写类工具可修改 data/（用例 / 套件 / 元素库 / 知识库 / 语音设置等）， 每次调用写 data/mcp_audit.log，长任务状态写 data/mcp_jobs/
GUI 与 MCP 同时开MCP 检测 data/gui.lock（GUI 启动即有单实例锁），自动降级为只读：dump / 截图 / 查询可用，操作类工具返回 PERMISSION_DENIED 并提示「先关闭虫师界面」
多个客户端连同一个 server允许；工具调用经 RUNTIME.lock 串行化，设备影响型任务再由 device_jobs 做互斥，避免两条指令同时发给设备
不做 HTTP 端口stdio 不监听网络，天然只限本机；生命周期跟随客户端，退出即结束，不留后台服务
⚠ 最容易踩的坑（先写在这里）：stdout 是协议通道，任何 print() / 第三方库的调试输出写进 stdout 都会让客户端解析失败。 server 启动第一件事就是 sys.stdout 只留给协议，把 sys.stderr 和 logging 全部指向 data/mcp.log。项目里 print() 不少（约 200 处）， 运行时必须整体重定向，别指望一个个改干净。

2. 统一返回与错误码：所有工具返回 { "ok": true, ... } 或 { "ok": false, "error": { "code": "...", "message": "...", "hint": "..." } }。 hint 是给人/AI 看的下一步建议，不要只报错不给方向。

错误码含义与建议

DUMP_FAILED层级读不出（界面一直在动/自绘 UI）：改用 screenshot + 图像匹配
ELEMENT_NOT_FOUND没命中：hint 里带 3 个「文本/ID 相近」的候选（复用 _diagnose_element）
ELEMENT_AMBIGUOUS命中多个：返回候选列表让 Agent 选 index，别自己猜

PERMISSION_DENIEDGUI 正在运行（MCP 降级只读）；写操作需先退出虫师

3. 超时默认值（不用 Agent 传，除非它明确要覆盖）： ui_find / ui_dump 20 秒（车机 dump 8~12 秒，留足余量）； tap / input_text 10 秒；wait_until 默认 10 秒、上限 120 秒； run_case / run_suite 的 wait=true 默认最多等 60 秒， 超时返回 run_id，任务仍在后台执行，用 run_case_status 轮询、 run_case_stop 停止。长任务（Monkey / 录屏 / logcat / 性能 / 抓包）启动即返回 run_id，由各自的 status / stop 工具管理。

4. 缓存策略：ui_find 用「最近一次 dump」，默认不重复 dump； 但距上次超过 3 秒或界面已变（tap 之后）必须重新 dump。 Agent 连续点同一个界面时不会退化成「每点一次等 8 秒」。

五、安全边界（本地工具，也要有边界）

  • 只走 stdio：不监听端口、不做 HTTP，天然只有本机进程能连。要开放给局域网？不做。
  • 工具白名单：不提供任意 adb shell 透传，不提供 root / remount / bootloader / recovery / fastboot。文件 push / pull 只接受明确的本地与 远端路径；安装 / 卸载 / 清数据 / 重启是独立工具，必须显式授权。
  • 危险动作需显式授权（allow_destructive=true）：安装 / 卸载 / 清空应用数据、 重启设备、弱网下发、删除用例 / 套件 / 基线 / 笔记、非 GET 接口执行； 用例里的清空/安装/卸载/停止/重启应用、电源键、熄屏/改方向同样默认拒绝， run_case / run_suite / save_case 都会扫描。
  • 审计日志：每次工具调用写 data/mcp_audit.log （时间 / 工具 / 参数摘要 / 结果 / 耗时）；长任务另写 data/mcp_jobs/<run_id>.json。出问题能复盘「到底是人点的还是 AI 点的」。
  • 用户数据写入：MCP 可以写 data/（用例、套件、元素库、知识库、 语音设置等），但必须通过明确的写工具、且 GUI 未运行；save_case 支持草稿预览与覆盖确认，不做隐式批量改写。
  • 设备任务互斥与清理：device_jobs 统一 run_id / watchdog / stop；设备影响型长任务互斥，任务进行中其他工具返回 DEVICE_BUSY。 主机侧任务随 MCP 退出而中断并标记 stale；设备端常驻的 Monkey 标记 detached，可按 PID 重新接上。弱网规则带设备端 TTL 兜底自动清除。
  • 端口/进程卫生：uiautomator2 首次连接会装 atx-agent，MCP 进程常驻而不是每次重连； 进程退出时清理自己拉起的 adb 子进程（复用 utils/win_job.py 那套）。

八、远期扩展：网页端使用虫师（可选，非本期）

为什么单独放远期：DeepSeek / Claude 网页版本身不能启动你本机的进程， 也就不能直接连本地 stdio 的 MCP Server。想让网页端用虫师，必须多一层 「本机 bridge + 公网中继」；这不是 MCP P0~P2 的一部分，也不应该为了它牺牲当前 「只走本机 stdio」的安全边界。

📌 2026-11-17 平台侧初步反馈（DeepSeek 网页端）：询问「是否支持自定义 MCP / 工具 connector」时，回复是有条件支持——支持自定义 connector，但必须是 「平台可控、权限最小化、可审计、需用户授权」，而不是模型无条件任意调用外部工具。 对方列出的约束：最小权限、用户确认、沙箱与隔离、密钥管理、审计与日志、 限流/超时/错误处理、数据隐私、可撤销。

三、配置方式与优先级

命令行参数写在客户端的 mcpServers 里，改一次要重开客户端，很别扭。 所以主入口放在虫师自己的配置文件里，命令行只做临时覆盖。

// data/mcp_config.json（可选；不写 = full）
{
  "tools": {
    "profile": "core",          // core | standard | full
    "add": ["gen", "ops"],      // 在 profile 基础上追加的组
    "remove": ["monkey_start"]  // 从结果里摘掉的单工具（组名也可）
  }
}

优先级：命令行 --tools= > 配置文件 > 默认 full。 这样三种人都照顾到了：

  • 不配的人：什么都不用管，就是 full（73 个，与升级前一致）
  • 阶段性调整的人：在 data/mcp_config.json 里改一行，下次连接生效，不碰客户端配置
  • 临时覆盖的人：命令行 --tools=core,gen,-save_case

命令行语法（与配置文件等价）： --tools=core,gen,ops（组叠加）、--tools=-monkey_start（从 full 排除单工具）、 --tools=full（全开）。启动日志会打印实际暴露数量，例如 MCP 工具：命令行 --tools=core，暴露 16/73 个。

预设定义：core = core；standard = core + content； full = 全部（默认）。standard 是给「既要执行、也要维护用例」的场景用的。

配置文件是可选的：不存在时按默认 full；不会在启动时自动生成， 需要收窄时手工创建 data/mcp_config.json 即可。

四、可发现性：主动收窄后，怎么让人找得到

先讲清机制：MCP 客户端在连接时向 server 要一次工具清单，把清单连同参数说明注入模型上下文。 模型能用的只有清单上的东西；不在清单上的，它不但调不了，而且根本不知道存在 —— 这不是「没权限」（会说需要授权），而是「不知道」（会让用户手动操作）。

B 方案下默认是 full，gen 一直在清单里，不存在「找不到」的问题； 只有用户主动切到 core 且没有 add: ["gen"] 时才会遇到。 对这类用户，当前补偿方式是文档 + 启动日志：

  • README / 帮助中心写明四个组分别包含什么，以及「需要现场生成用例时加 gen」；
  • 启动日志打印 MCP 工具：配置 profile=core，暴露 16/73 个， 用户能立刻看出自己收窄了哪些能力。

没有往 list_cases / run_case 的 description 里加提示： 那会改变已实测的 schema 预算，而且默认 full 时并不需要。如果以后把 core 改成默认， 再把「缺少用例时提示开启 gen」补进 description。

💡 打个比方：工具清单就是工作台面上摆出来的工具。默认全摆在台面上； 用户自己把三件收进抽屉时，我们至少在抽屉上贴张字条（文档 + 启动日志）。

五、设计决策记录（为什么这样，为什么不那样）

① 为什么 B 保留 full 默认：不在清单里的工具对模型是静默消失 （既不能调，也不知道存在），而 1.6.0 本身已经有 MCP 接入、weditor 下线、依赖大改等变更； 默认切 core 会把「省 token」与「工具突然不见了」混在一起，很难归因。 先用 opt-in 收集真实使用数据，再决定是否改默认。 至于 core 本身为什么不含 gen：用例总量有上限、集中在项目初期， 中后期以回归和零星补充为主；1173 字符（全量 11%）换一个阶段性能力不划算 —— 这是 「切 core 时」的取舍，不是当前默认。

② 为什么不按工具名前缀自动分组：现有命名是动词开头 （list_cases / save_case / run_case / explore_and_draft / press_key / launch_app）， 按 _ 前缀分会碎成 26 个组、其中 13 个各只有 1 个工具。 所以必须显式标注组（当前维护一张 mcp_server/tool_groups.py 映射表）。 兜底防烂：未标注的工具自动进 core，不会变成「找不到」； 当前 73 个工具均已标注，启动日志会打印实际暴露数量。

③ 为什么不做运行时动态增删（notifications/tools/list_changed）： 协议支持，但客户端实现参差，常见「列表刷新了、模型还在用旧的」；收益远小于麻烦， 改配置后重连一次反而确定。

④ 为什么不做懒加载（先给 8 个，模型需要时调 request_tools 加载更多）： 多一轮往返，且多数模型不会主动去加载，「不知道自己不知道」的问题反而更严重。

六、由此发现的一个新能力：跑完回存

讨论「横展」时发现一个比 explore_and_draft 更贴合真实动作的工具：

save_run_as_case —— 把一次 run_case 实际执行过的步骤（含每次点击命中的 控件与定位值）存成新用例。

⚠ 前置改造（当前不具备）：run_case 的 StepResult 只有 index / name / type / ok / message / screenshot，没有 params； CaseRunner 只在失败上下文里记录 step_params， 成功执行时并没有留存命中的控件与定位值。要实现「含定位值」，需先让 CaseRunner / DeviceService 在成功执行时也记录步骤参数与命中元素， 约 100~150 行；工具本身约 50 行，不能按「只加一个工具」估算。
💡 为什么它比「边探索边记」更实用：横展到新车型时的真实动作是 「先在这个界面上手点一遍看能不能跑通」，跑通了才想「这套步骤存下来」。 explore_and_draft 适合全新流程，而这个适合验证成功后回存。 横展到别的项目时，这套已存的用例还能用 case_copy（content 组）直接复制。

归属：gen 组；触发提示挂在 run_case 的返回里 （「本次执行 8 步，如需存为新用例，开启 gen 组后用 save_run_as_case」）。

横展的两种情况要分开：
① 同构横展（新车型界面一致）→ 复制已有用例改定位，case_copy + element_upsert 就够， 不需要 gen；
② 异构横展（界面不同、旧用例全废）→ 才需要重新探索/回存，走 gen。

四、P3（加固）：console=False 与 stdout

mcp_server.spec 明确写了 console=False（不弹黑框），注释理由是 「stdio 句柄由 MCP 客户端通过管道提供」。但实际链路是：

  • mcp_server/server.py::main() 只做两件事： device_jobs.init() → setup_stdio_logging() → server.run("stdio")
  • mcp_server/logging_setup.py::setup_stdio_logging() 接管了 sys.stderr 与 builtins.print（把约 200 处 print() 重定向到 data/mcp.log），但没有碰 sys.stdout

问题（理论风险）：PyInstaller 的 windowed 构建在没有有效 stdout 句柄时， sys.stdout 会是 None；MCP 的 stdio 传输需要向 stdout 写 JSON-RPC 帧， 遇到 None 会抛异常或静默失败。需要注意这是条件成立的： 当客户端用管道拉起进程（所有标准 MCP 客户端都是这样）时，stdout 句柄有效，不受影响。

实测结论（2026-11-17）：本机多次用 dist_mcp\虫师-mcp.exe （console=False）通过管道调用 tools/list 与真实工具， 均正常返回 73 个工具，没有复现「列表为空 / 超时」。早期确实只用 python main.py --mcp 冒烟过，但后续已经用打包版反复验证。 因此这条从 P1 降为 P3：保留「stdout 为空时重开 fd 1」作为加固， 不再作为发版阻塞项。

修法（加固，建议做但不阻塞）：

  • 改 console=True：最稳，代价是客户端拉起时一闪而过一个黑框 （多数 MCP 客户端在后台拉进程，用户基本看不到）。
  • 启动时重开 stdout：在 setup_stdio_logging() 里加 sys.stdout = os.fdopen(1, "wb", 0)（并给 sys.stdout 为 None 的情况兜底日志），保持无窗口。 前提是父进程确实把管道句柄传给了子进程——不同客户端行为不一致，需要实测。
💡 处理原则：协议层已用现有打包版验证通过；加固只在 setup_stdio_logging() 里补 stdout 兜底即可，不要为了「有没有黑框」 同时改动构建模式与启动逻辑，否则两个变量一起变很难定位。
